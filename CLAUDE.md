# tradedesk

Short-term momentum scanner for NSE stocks using the INDstocks (INDmoney) API.
Evening scan on daily charts, live trigger monitoring, trades held hours to 10 sessions.
It alerts; the human places every order.

## Hard rules
- NEVER call or implement order placement, modification or cancellation unless the task explicitly says "Milestone M12".
- The API reference is docs/indstocks-api.md. Never guess endpoints, fields, formats or limits; read the doc.
- Every INDstocks call goes through broker/indstocks/ratelimit.py. Never exceed documented limits.
- NEVER hardcode tokens or the TOTP secret. Tokens live in memory; the TOTP secret comes from keyring.
- The live scanner and the backtester share engine/engine.py. No live-only or backtest-only signal logic.
- Fills are gap-aware everywhere: an open beyond a stop or trigger fills at the open.
- Overnight positions are long-only.
- No feature, signal or label may use data from after its timestamp. Every setup and feature has a look-ahead or leakage test.
- Portfolio limits (heat, positions, sector caps, daily and weekly limits) apply in backtests, paper book and live alike.
- Fail closed: stale data, a disconnected feed or API errors pause alerts and raise a health alert.
- Never block the asyncio event loop; CPU-heavy work runs in a worker thread.
- Timezone is Asia/Kolkata. Candle logic uses exchange timestamps, not the local clock.
- Claude output is advisory text only; it can never create a signal or change a price, level or quantity.
- The prediction layer can only lower grades or size, never raise size beyond config caps.
- Changes under engine/, setups/, live/ or data/ must pass tests/replay and tests/gaps.

## Conventions
- Money and rates are `Decimal`, never float. Config percentages are fractions (0.001 = 0.1%).
- Cost lines are rounded half-up to the paisa individually before summing; STT and stamp duty are rounded to the nearest RUPEE per trade (ledger-verified: Rs 0.86 STT -> 1, Rs 0.13 stamp -> 0). GST = 18% x (brokerage + exchange txn + SEBI) - not IPFT/STT/stamp. Brokerage = 0.1% capped at Rs 5 with a Rs 2 minimum (Muhurat reversal 2.36 = 2 + GST).
- Net R:R = (gross reward − costs to target) / (gross risk + costs to stop). A stop-out loses more than 1R. PLAN.md §7's worked numbers (1.4R/2.3R, ~₹110) assume ₹20/order; INDmoney actually charges 0.1% capped at ₹5 (min ₹2) per order, so the same card is ₹72 and 1.61R/2.48R.
- The cost calculator never infers intraday vs delivery; the caller passes `TradeType`. Same-day buy+sell is INTRADAY.
- Charge rates live in config/risk.yaml under `costs:`. Real contract-note figures live in tests/golden/contract_notes.yaml; if INDmoney changes pricing, update both.
- tests/golden/rate_card_examples.yaml + test_rate_card.py are a PROVISIONAL stand-in for the missing intraday golden notes: hand-computed from the documented rate card, not a real bill. They are never the M1 done-when count (test_golden_coverage_report reads contract_notes.yaml only) - delete rate_card_examples.yaml once a real intraday note lands there.
- INDstocks facts baked into broker/indstocks/: REST codes are `NSE_3045`, WebSocket codes `NSE:3045`; candle `ts` is the OPEN time in epoch seconds, requests use epoch ms; ≤5 codes per candle call, ≤1000 per quote call, ≤3000 instruments per WS connection; one TOTP token live at a time (24 h, 1 generation/min).
- The doc's FAQ section contradicts the endpoint pages (different WS URL, `symbols` param). Follow the endpoint pages and the OpenAPI spec, never the FAQ.
- Market-data prices are float (pandas/DuckDB bound); accounting money is Decimal.
- Indicators (engine/indicators.py) are hand-written pandas with TradingView conventions (ema seeded on first value; rma = Wilder, SMA-seeded, na until n finite values; population stdev). No TA-Lib: its C DLL would hit Smart App Control.

  **M11 rigor pass (2026-09-12)**, from a user-supplied "ML Prediction Layer Improvement" PDF: an Explore-agent audit found most of the PDF's asks (baseline+challenger, purged walk-forward, shadow-mode, leakage tests) already built, so this pass targeted only the verified gaps. (1) **A genuinely locked final test set** - `train()` now reserves the most recent `final_test_frac` (default 20%) of history BEFORE walk-forward folds ever see it; model AND threshold selection happen only on the earlier "dev" data, the reserved block is scored exactly once with the already-chosen model/threshold (`TrainReport.final_test`) - previously the same walk-forward OOS predictions fed both model selection and the reported metric, which is a real (if subtle) form of leakage into the "out of sample" number. (2) **Full ML metrics** - `evaluate()` now also computes ROC-AUC/PR-AUC/precision/recall/F1/log-loss (degrading to `None` on a single-class fold rather than raising). (3) **Reproducibility** - every estimator now takes a `seed` (default `DEFAULT_SEED = 20260101`), including `CalibratedClassifierCV`'s internal `StratifiedKFold`. (4) **Complete artifacts** - the `.json` sidecar now carries `training_data_range`, `feature_version` (`features.py::FEATURE_VERSION`, bumped to "v2"), `target_definition`, `hyperparameters`, `random_seed`, `feature_list` (previously joblib-only), `final_test`, `threshold_grid` and the top-10 `feature_importance` - previously only 6 of the PDF's 10 requested fields existed and none were tested; `tests/prediction/test_prediction.py::test_artifact_json_has_every_field_the_bundle_promises` closes that gap. (5) **`ModelBundle.feature_importance()`** - kind-agnostic (logistic coefficients by magnitude, or `.feature_importances_` for a tree model), where the old `coefficients()` only worked for logistic and silently returned `None` otherwise. (6) **XGBoost added and it WORKS here** - unlike LightGBM, `uv add xgboost` (3.4.1) both installs AND imports cleanly, no Smart App Control block; `make_xgboost()` mirrors `make_lightgbm()`'s exact guarded-import pattern and competes in the same OOS-Brier race. (7) **`prediction/train.py::compare_strategies()`** - the actual economic question the PDF's Strategy A/B/C section asks for: joins the trained bundle's probability to each closed trade via `t.position.signal.id` (the same join `build_dataset` already uses) and reports `backtest/reports.py`'s `metrics()`/`max_drawdown()` plus two NEW functions, `sharpe_ratio()` and `cagr()` (there was previously no Sharpe or CAGR ANYWHERE in this repo), for "all triggered signals" vs "probability >= threshold" side by side. Strategy B (ML-only, no rule gate) is explicitly out of scope - nothing but `engine/engine.py::scan_day` may create a signal. (8) `select_threshold()` grid-searches 0.50-0.80 on VALIDATION-fold predictions only (never the final test set) and reports a `has_edge` flag. (9) Two new features, `nifty_return_1d/5d` (`market_context()` in train.py, sourced from `md.benchmark` - already loaded for the regime calc, no new data pipeline) - `sector_return_1d/5d` was deliberately NOT added: `config/universe.yaml`'s `sector_indices` list (9 real NSE sector indices) turned out to be completely unused anywhere in the codebase, and `sector_percentile` (the existing sector feature) is ALSO never actually populated by any real caller (always defaults to 50.0) - building sector_return properly needs a stock-to-sector-index mapping and sector candle loading that doesn't exist yet, a real follow-up, not a two-line addition.

  **Two real bugs found by actually running this on live NSE data** (2023-09-01 to 2026-09-12, 2,639 codes), not found by unit tests alone: (a) `select_threshold()`'s original "maximise total R" rule had no minimum-sample floor, so on real data where EVERY threshold in the grid showed negative expectancy, it picked 0.80 purely because that threshold happened to leave exactly 1 trade (least to lose, not a real signal) - fixed with a `min_above` floor (default 20) and a `has_edge` flag that goes `False` when even the best eligible threshold is net-negative, so the report says "no threshold shows real improvement" instead of presenting a statistically meaningless pick as a discovery. (b) `equity_curve_from_trades()` initialised every calendar day to `starting_capital` instead of `NaN`, so `.ffill()` had nothing to propagate and any day after the last trade's exit silently reverted to the STARTING capital - combined with plain `pct_change()`'s Jensen's-inequality bias on a lumpy equity curve (a flat round trip up-then-down has a spuriously POSITIVE arithmetic mean return), the real run first reported Sharpe +1.416 alongside CAGR -16% for the SAME losing strategy. Fixed both: the equity curve now starts `NaN` (`.iloc[0]` = capital) before `.ffill()`, and a new `backtest/reports.py::log_returns()` (additive, no Jensen's-inequality bias - a round trip nets to exactly 0) replaces `pct_change()` for Sharpe. Re-run after both fixes: Sharpe -4.701, correctly agreeing in sign with CAGR -16.04%. Regression tests for both: `tests/backtest/test_reports_metrics.py`.

  **The honest finding, now trustworthy** (previously would have been corrupted by bug (b) above): re-running `tradedesk train --from 2023-09-01` end to end on the full real universe gives Strategy A (existing rules, unchanged) 615 closed trades, win rate 26.7%, expectancy -0.557R, net P&L -Rs 41,109, CAGR -16.04%, Sharpe -4.701, 41.1% max drawdown - i.e. **the existing rule-based NSE setups have been net-negative over this specific 2023-2026 window**, independent of any ML question. The model's own OOS metrics (ROC-AUC 0.556, barely above a coin flip; base rate 27%) show weak discriminative power, and no threshold in the standard grid shows positive expectancy with an adequate sample - `has_edge=False`. This mirrors the M13 crypto verdict's honesty (`-0.515R expectancy... do NOT trade these setups`): the ML rigor pass makes the pipeline trustworthy, but trustworthy currently means "confirms there is no edge to filter for" on this window, not "found one." Full artifact: `data/models/20260912-201347.json`; dataset: `data/reports/ml_dataset_v2.csv` (29,834 triggered signals, base rate 0.27).
